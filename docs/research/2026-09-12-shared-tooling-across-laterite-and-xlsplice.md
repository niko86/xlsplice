# Shared tooling across laterite and xlsplice

Surveyed 2026-09-12 against `niko86/laterite` and this repo as they stood that
day.

Every claim below was read out of one of those two trees, and quotations are
copied from the file named beside them rather than paraphrased. Counts and line
numbers are a **dated snapshot of a moving tree**, not maintained figures; where
one is load-bearing, the instrument that produces it is named so it can be re-run
instead of trusted. Anything asserted without a file behind it is marked
**(synthesis)**.

The question: what tooling `laterite` has built that a second repo could use,
what should move out of it, and what this repo should take now.

## 1. Why the question is live

`laterite`'s tooling outgrew its product. `tools/` holds sixty-odd scripts,
`ags-wiki/.bootstrap/` is ~2,700 lines of Python driving ~450 pages, and the root
`tests/` suite is ~12,000 lines that exist only to test the gates.

None of that is a shipped artifact, which matters because
`ags-wiki/design/dec-monorepo-structure.md` — the decision that rules out
per-component repos — governs the crates, not the tooling. Its reasons are one
dictionary source of truth and atomic cross-language changes in one CI run;
neither says anything about a linter that reads Markdown. So the tooling layer is
answerable without contradicting that decision, and the crate layer is not.

This repo is the other half of the question. It is a second Rust CLI in the same
house style, and where it re-solves something `laterite` already solved, that is
either a chance to share or a sign that one of the two is wrong.

## 2. What is shared by hand, and what only looks like it

`laterite` states the rule, in `ags-wiki/concepts/agent-first-cli-contract.md`:

> duplication across CLIs is resolved by **extracting a shared crate**, never a
> documented copy.

It is honoured inside the workspace and broken at one repo boundary that counts.

**The CLI output contract.** That same page names the lineage: "the **gogcli →
discrawl → cli-printing-press → ags5db** lineage (the first three are external
sibling tools, *not* in this repo; the convention is what carried over)." `lat`
is the fifth and this repo is the sixth. The shared crate exists —
`laterite-cliutil` — and is `publish = false`, so nothing outside that workspace
can reach it. The convention crosses repos; the code cannot. This is the one
genuine instance.

**Inside `laterite` itself**, the same thing happened at module scale and was
already fixed: `tests/_tools.py` exists because a path-loader had been written
thirty-three times, "each guessing independently whether to register the module in
`sys.modules`". That extraction is the precedent, and it is the reason to believe
the instinct rather than the tidiness.

**What is *not* an instance**, though it looks like one at first: the
`docs/agents/{domain,issue-tracker,triage-labels}.md` trio that both repos carry,
and the ~200-line wizard library at the top of `scripts/save-fixtures.sh`. Those
are distributed by skills — the trio maps onto `mattpocock/skills`' canonical
roles, and the wizard header says "Generated by the /wizard skill" — with a
per-repo config file as the seam. That is not duplication anyone here owns; it is
skill-distribution working as designed.

They are worth naming anyway, because they are the **precedent for how the wiki
tooling below should travel**: a skill that carries the machinery and leaves a
small config file in each repo is a shape already proven twice in these two trees.

## 3. The wiki / knowledge-base system

The largest and most transferable thing `laterite` has built, and the one where a
skill is the point rather than a wrapper.

### 3.1 What is there

`ags-wiki/.bootstrap/`, stdlib-only throughout (`re`, `json`, `subprocess`,
`pathlib`, `difflib`, `tomllib`, `collections` — no third-party dependencies):

| file | lines | what it is |
|---|---|---|
| `lint.py` | 1,896 | the enforcer — A1–A13, B1/B2, C5/C6, D1/D2/D4/D5/D7 |
| `librarian.py` | 242 | "which pages cover these files?", by inverting citations |
| `reindex.py` | 198 | `index.md == render(vault)`, with `--check` |
| `check_ext_drift.py` | 165 | external-citation drift, weekly, report-only |
| `refs.py` | 149 | the citation grammar the others share |
| `wiki-classes.json` | 24 | the entire domain configuration |
| `templates/*.md` | 12 files | one per class — the front-matter *is* the schema |

`.github/workflows/wiki-lint.yml` runs it with `uv run --no-project`: no
`uv sync`, no wheel, no Rust build. That portability is stated as a hard rule in
three places, and it is what makes "point this at any repo" possible at all.

### 3.2 The clean core: `refs.py` + `librarian.py`

~400 lines together, and already engineered to be lifted.

`refs.py`'s own docstring is the argument for its existence: it was pulled out of
`lint.py` "so a second tool can resolve a citation without importing the linter",
and it is "import-safe by construction: no top-level I/O, no argument parsing,
nothing but constants and pure functions." `ref_covers`, `strip_ref_suffix`,
`_expand_braces` and `frontmatter_block` are already pure and root-free.

`librarian.py` already takes a vault path *specifically* so a caller can point it
at another vault — its `Hit.rel` docstring says so — and
`tests/test_librarian.py` is nine tests against a `tmp_path` vault whose names map
one-to-one onto the invariants an extracted unit would need
(`test_an_exact_citation_outranks_a_directory_sweep`,
`test_a_directory_only_hit_says_so`,
`test_the_cap_holds_and_declares_what_it_dropped`, and so on). The tests travel
with the code, and they never assert a live page pair, deliberately: a test that
did "would go red the day someone legitimately moved a citation, turning a lookup
convenience into a brake on wiki edits."

**The idea worth carrying is the coverage honesty split.** `ref_covers`
distinguishes *exact*, *glob* and *ancestor*, and its docstring carries the
measurement that justifies it: only about one in five tracked files is cited
exactly, and most apparent coverage comes from a page citing a directory — one
`repo:web/` citation sweeps hundreds of files from two pages that describe none of
them. So an ancestor-only hit prints `(directory only — may not describe this
file)`. A lookup that hid that would be worse than no lookup at all.

Three changes are needed, all small:

- `refs.WIKI = parent.parent` / `REPO_ROOT = WIKI.parent` hard-wires "the vault is
  a direct child of the repo root". Take an explicit `(vault_root, repo_root)`
  pair instead.
- `path_exists` and `resolve_ref` read a module-level `REPO_ROOT`. Pass the root.
- `librarian.SKIP_STEMS` contains the literal `"AGS-WIKI"`, and `CLASS_ORDER` is
  the AGS twelve. Both belong in the class config.

Two comments in `librarian.py` record checks deleted because **mutation testing
proved they could never fail**. Carry those comments across; they are the best
evidence the file has been thought about, and without them they read as missing
checks to whoever arrives next.

### 3.3 The config that already makes it generic

`wiki-classes.json` is the single source of the class list, and its `_note` is the
whole argument in miniature: "Previously both hand-duplicated the list — the
enforcement machinery had the same multi-source-of-truth rot it exists to catch."

Six of its twelve classes are generic — `concepts`, `design`, `tools`, `sources`,
`insights`, `strategies`. Six are AGS — `rules`, `groups`, `types`,
`observations`, `editions`, `comparisons`. A shared tool ships the schema and the
generic six as a default; `laterite` keeps its own file untouched and becomes a
consumer of its own machinery.

The same holds for templates. The convention — one `_template-<class>.md` per
class, `_`-prefixed, TODO-marked, **and its front-matter read at lint time as the
required-key set** — is fully generic. `lint.py`'s B1 check does exactly that:

> Each `_template-<class>.md`'s own frontmatter block IS the required-key set for
> its `type:` — read it at lint-run time so a template edit updates the check
> automatically, with no second copy to fall out of sync.

Four of the twelve templates are class-neutral (concept, decision, comparison,
source). Ship those; keep the rest as an example corpus.

### 3.4 The blocker: `lint.py` needs splitting, not lifting

The real cost, and it should be named before anyone starts.

`lint.py` has no `argparse` — it reads `sys.argv` at module scope — keeps
module-scope state, and calls `sys.exit()` at the bottom. It is **not importable**.
The proof is in the tree: `check_ext_drift.py` obtains `EXT_ALLOWLIST` by regexing
`lint.py`'s *source text*, and documents why — "importing it would execute its
whole top-level" — calling it the lesser of two evils against a second copy. A
shared config file is precisely what removes that wart.

Roughly two-thirds of its checks are generic: wikilinks resolve, orphan pages,
mermaid fence balance, template-derived front-matter schema, status vocabulary,
`related:` reciprocity, superseded-needs-a-tombstone, `owns:` uniqueness, the
dead-reference scan, the retired-terms tripwire, the `ext:` allowlist, historical
markers, and the ratchet. The other third reads `rust-packages/*/Cargo.toml` via
`tomllib` and `ags_dictionary.json` via `json` — the crate-map agreement checks,
the `erDiagram` group-code check, the reliquary register.

So: give it an argparse surface and a `main()`, split the Cargo and AGS checks
behind a plugin the host repo registers, then extract the core. After the clean
core has proved the shape, not before.

### 3.5 The idea that makes adoption possible: the ratchet

`wiki-lint.yml` runs `lint.py --since origin/<base>`, which "grandfathers every
pre-existing dead `repo:` ref / retired-term mention and fails ONLY on rot
introduced by lines this PR itself added or modified." Whole-vault enforcement
lives in the nightly, and the pull-request lane is advisory on purpose:

> keeping the wiki aligned is the maintainer's job, and a contributor should not
> have a PR blocked because a page they never touched cites a file that moved.

That advisory-ratchet plus enforcing-nightly split is what lets a gate be adopted
on a repo that would not pass it whole — which is every repo that adopts one.
`check_spelled_counts.py` applies the same shape to a different rule, so the
pattern is proven twice.

Two governance lessons ship with it, each stated independently in three
`laterite` workflows:

- **Never put a `paths:` filter on a required check.** "the requirement sits
  PENDING forever and the PR cannot merge — the only way through is the admin
  bypass button." `laterite` did this once and merged every outside-path PR by
  bypassing branch protection until it was found.
- **A job's `name:` *is* the ruleset context string**, with nothing linking the
  two, so renaming a job silently makes the repo unmergeable.

Both apply here the moment this repo's CI grows past one job.

### 3.6 Near-verbatim bonus: `gen_wiki_tables.py`

About a hundred lines, and self-describing: each source JSON declares its own
`target`, `marker`, `fields` and `rows`, so extending the family is "a new JSON …
plus the matching BEGIN/END markers in the target `.md`. **No new code needed.**"
The only repo-specific line is a two-entry `SOURCES` list. Marker convention is
`<!-- BEGIN GENERATED: <marker> -->` / `<!-- END GENERATED: <marker> -->`.

### 3.7 What a skill would do

Maintaining a vault has a real running cost — a visible share of `laterite`'s
recent commits are wiki repairs — so a tool without a skill just moves that cost
around. Four verbs **(synthesis)**:

1. **`scaffold`** — drop the bootstrap, the generic templates and a starter class
   config into a repo that has none; wire the advisory PR lane and the enforcing
   nightly; write the `docs/agents/domain.md` adapter that tells other skills the
   repo's *why* lives in a vault. `laterite`'s own `domain.md` is the model, and
   exists precisely because "this repo does **not** use the `CONTEXT.md` +
   `docs/adr/` layout the skills otherwise assume."
2. **`cover`** — run the librarian before editing, and before publishing any claim
   about how the repo behaves.
3. **`page`** — create a page from its class template, so the front-matter is
   right by construction.
4. **`sync`** — refresh the copy in a consuming repo and re-run the drift check.

### 3.8 Order

| stage | what | cost | unblocks |
|---|---|---|---|
| 1 | `refs.py` + `librarian.py` + the class-config schema, root-parameterised, tests carried over | small — mostly already done | `cover`, usable anywhere immediately |
| 2 | `gen_wiki_tables.py` + the marker convention | tiny | generated tables anywhere |
| 3 | `reindex.py`, with the title, Related footer and Gaps bullets templated out | small | `scaffold` |
| 4 | split `lint.py`: argparse, `main()`, a host-plugin seam, then extract the generic core | the real work | the full kit; also kills the `check_ext_drift` source-regex wart |
| 5 | templates as an example corpus, plus the `domain.md` adapter | small | `page`, and skill interop |

Stage 1 is independently useful, which is the test of whether the order is right.

## 4. The gate family

All twenty-one `tools/` scripts are standalone and stdlib-only. There is **no
shared library**: `ROOT = Path(__file__).resolve().parent.parent` is written out
once per script, `tomllib` manifest reading is reimplemented seven times, and the
only cross-imports are three `sys.path.insert` hacks.

Cleanest candidates, in order:

1. **`tools/issue_tracker.py`** — the single cleanest lift. It is already a library
   with three config instances
   (`class Tracker(NamedTuple): title, marker, body, changed, closed`) and says so:
   "adding a second is a config rather than a fork of the state machine."
   `plan_items()` is pure and `main()` is the only line touching the world, which
   is why it is testable without a GitHub API.
2. **`tools/check_external_authorities.py`** — already fully flag-parameterised
   (`--mirror`, `--tree`, `--repo`) with no hardcoded paths, because it was written
   to run against a different repo.
3. **`tools/check_issue_refs.py`** — the squash-merge watermark, where a number
   below the highest merged PR is released from the foreign set automatically, is
   novel and repo-agnostic.
4. **`tools/check_doc_refs.py`** — the canonical example of the scope rule below.
   Two resolution rules: a repo doc resolves doc-relative then repo-root; a
   published crate's README resolves strictly inside the package, because
   crates.io serves only packaged files.
5. **The Rust release gates** — `check_msrv.py` (the toolchain comes *from* the
   manifests, because "hard-coding 'test on 1.85' beside a manifest that says 1.85
   is two statements of one fact"), `check_semver.py` (reports per crate whether it
   was `enforcing` or `ahead`, because once a bump lands the tool enforces nothing
   and a green run would be a lie), `check_public_api.py`,
   `check_package_contents.py`.

**One convention worth finishing during any extraction.** `laterite`'s rule that a
gate reports its own scope has around a dozen hand-rolled implementations and
three different flag spellings — `--skipped` twice, `--list` three times, nothing
elsewhere. `check_doc_refs.Scan` is the reference implementation, and its comment
says why it is a two-field type: "so a caller cannot report the verdict without
having been handed the scope it was reached under."

**Not extractable:** `gen_census.py`, `gen_modality.py`, `gen_observations.py`,
`gen_doc_outputs.py`, `check_speed_claims.py`. Their ideas travel — reflect rather
than hand-list; derive rather than store; keep a record's body verbatim and let
`--lint` report house-style departures without rewriting them; make the `.out`
file the artifact so nothing is copied into the page — but the code is AGS-wired
throughout.

**And the counterweight**, which belongs beside any generator scaffolding —
`check_support_matrix.py` on when *not* to build a JSON source of truth:

> That idiom (`changelog.json`, `observations.json`, `modality.json`) earns its
> ceremony over 174 groups or 50 observations. Over four rows it is pure overhead.

## 5. The CLI output contract

The one candidate with a live second consumer: this repo, right now.

`laterite-cliutil` is ~940 lines; its `report.rs` calls itself "Report dispatch —
the CLI output contract, in crate form." This repo reimplements roughly 1,400
lines of the same contract:

| cliutil | here | lines |
|---|---|---|
| `Ctx` / `Report` / `emit` | `src/answer.rs` + `src/render.rs` + `src/out.rs` | 570 + 359 + 109 |
| `write_atomic` | `src/atomic.rs` | 223 |
| `write_json_pretty` / `write_ndjson` | `src/envelope.rs` | 158 |
| `OutputMode`, `styled_table` | `render::OutputMode`, `Shape::Rows` | — |
| `print_readme_if_requested` (`--readme`) | absent — open as #17 | — |
| `Spinner` / `progress_bar` / `MultiLine` | deliberately unwanted | — |

**No publish would be needed.** All three cliutil consumers — `laterite-cli`,
`laterite-ags4-corpus-qa`, `laterite-ags4-forge` — are `publish = false`; only the
`laterite` facade is published, and it does not use cliutil. So a git dependency
would serve, and the irreversible crates.io naming decision — the one
`laterite-ags4-excel`'s manifest records the hard way ("A crates.io name cannot be
changed after the first publish") — never has to be made.

The crate would have to be split first. Its progress half pulls `indicatif`,
`console` and `comfy-table`, and this repo deliberately has neither colour nor
progress UI: `Cargo.toml` says "the contract says human output is plain, so clap's
`color` feature is left out rather than switched off at runtime." So a lean
contract crate with `serde` and `serde_json` only, plus an optional tty feature.

### Where the sources argue against the current design — on laterite's side

`laterite`'s version of this contract is the weaker one, and this repo has already
named why.

cliutil's `Report` has each implementer hand-write `render_table` while
`full_value()` comes free from `Serialize` — two independent paths over one set of
data. `Answer::rows(payload, headers, rows)` builds both shapes in one constructor
and enforces the arity invariant once:

> This is the one place the arity invariant lives … so a verb that builds one is
> refused here, once, rather than by a hand-written test per verb.

Issue #25 is tightening it further, and names both the residual drift (enums
matched once for the envelope and again for the table) and the trap inside it
(`serde_json` writes `1e+300` where `f64`'s `Display` writes three hundred
digits). `laterite`'s `Report` has the same structural drift and has not named it.

**So the merge goes this way round, and it goes after #25.** Sharing the contract
before then would publish the weaker design and force a second migration.

## 6. What laterite should borrow back

Two more, beyond `Answer`.

**The contract observable without a process.** `render(Result<Answer>, OutputMode)
-> Rendered` returns both streams and the exit code as values, so the whole machine
contract is unit-testable; the suites dropped from around forty-eight spawns to
fourteen without losing coverage (`7c06fd4`). The panic hook routes crashes through
the envelope so "no failure mode is unparseable", and exits from the hook rather
than unwinding, because skipping destructors is what the "non-zero means nothing
was written" guarantee wants. `laterite` has no equivalent guarantee.

**Two doc conventions.** `CONTEXT.md` as a glossary with explicit `_Avoid_:`
banned-synonym lists, including deliberate disambiguation of two real collisions —
worksheet *envelope* against JSON *envelope*, defined-name *scope* against command
*target*. That one is gateable: a banned-synonym ratchet is a sibling of
`check_spelled_counts.py` and a natural addition to the lint core in §3.4. And
fixtures as an immutable byte baseline, with checksums committed beside them and
the rule "If one of these ever changes, a fixture was re-saved and the baseline
moved. **That is a bug, not an update.**"

## 7. Recommendations for xlsplice

Nothing here needs a shared repo, an extraction, or anyone else's schedule.
Ranked against this repo's stated CI-minutes budget.

1. **The missing Rust hygiene gates.** There is no `cargo fmt --check`, no `cargo
   clippy`, no `rust-version` despite `edition = "2024"`, no `clippy.toml`, no
   `deny.toml`. `laterite` has all of them under `rust-packages/`. fmt and clippy
   cost seconds on the cache `test.yml` already warms, inside the job that already
   exists — so this fits the budget rather than spending it.
2. **Cross-platform build coverage.** CI is Linux-only while the real targets are
   the dev Mac and the Windows lab machine. `src/atomic.rs`'s temp-file-and-rename
   and the zip round-trip are exactly the paths where that bites, and neither is
   ever compiled for either platform today. `cargo check` on macOS and Windows is
   far cheaper than `cargo test` and closes most of it. **This is the sharpest
   real risk found in either repo.**
3. **A public-API gate.** `src/lib.rs` declares every module `pub` and re-exports
   a dozen items, with `src/main.rs` as the only consumer: a large, undeclared,
   unguarded surface, in a crate whose whole contract discipline is otherwise
   explicit. `check_public_api.py` / `cargo-public-api` is the pattern.
4. **A doc-reference gate.** `README.md` already advertises `props`, `calc` and
   `diff` verbs that do not exist, and nothing catches it.
   `tools/check_doc_refs.py` is built for this class.
5. **`--readme` / help topics** — already open as #17, and
   `print_readme_if_requested` is the existing implementation, so it rides in with
   §5 whenever that happens.

**Not recommended here**, deliberately:

- **The changelog machinery.** Commit messages here are narrative design records
  ("The per-verb suites stop going round through argv"), not conventional commits.
  `gen_changelog.py` reads a hand-maintained `changelog.json`, so it would not
  actually fight them — but `check_changelog.py`'s value is gating a shipped
  surface against a release train that does not exist here yet. Revisit at the
  first tagged release (#18).
- **A vault.** ~450 pages of estate is the cost `laterite` is visibly paying every
  week. `CONTEXT.md` plus `docs/adr/` is doing the same job here at a fraction of
  it, and doing it better in the ways §6 describes.
- **The forty-gate CI surface.** The budget in `CLAUDE.md` is a stated, reasoned
  constraint, not an oversight, and `test.yml`'s header names what is excluded and
  where it belongs instead.

## 8. If a shared repo is ever stood up

Not proposed as work. Recorded because the two constraints below are easy to get
wrong later and cheap to write down now.

**Vendor a copy; do not submodule.** `laterite` is public, invites outside
contributors, and runs public CI. A submodule or git dependency pointing at a
private shared repo breaks `git clone --recurse-submodules` and every CI run for
anyone without access — which is every outside contributor, and the point of that
repo being public. Making the shared repo public instead would export
half-generalised internal tooling with a support surface attached.

Copying also has the better argument behind it. `laterite` already prefers
duplication with an agreement test over a shared import, and says so where it does
it: `tools/gen_crate_graph.py`'s `crate_deps()` is byte-identical to `lint.py`'s
by a gate rather than an import, because "lint.py is deliberately self-contained /
stdlib-only, so a shared import is avoided in favour of a gate." A vendored copy
with a drift gate is that same pattern one level up.

The pin shape already exists at `laterite/tools/vendor/laterite-duckdb-functions.json`,
which vendors across a repo boundary today and states the discipline: the copy "is
not live: it goes stale by design, and refreshing it is a deliberate act, not a
sync", and refreshing means re-adding the pin block, because the gate "fails
without it, on purpose". A pin carries what the copy is, why it is here, how to
refresh it, and the upstream path and revision.

This repo is private throughout, so it is unconstrained: a submodule or a git
dependency would both work here, and for the §5 crate a git dependency is simplest.

**Extract only once a second repo wants it.** `dec-monorepo-structure.md` settled
the equivalent question for the crates — a carve-out happens against a named
trigger, "never as a speculative 'cleaner structure' move." That decision does not
bind the tooling layer, but adopting its reasoning keeps the two answers consistent
instead of leaving a loophole where dev tooling escapes the rule the product obeys.

The qualification that makes the rule usable: the second consumer does not have to
exist, it has to be **named**. §5 qualifies because this repo is reimplementing the
contract now. §3.2 qualifies because both repos are named consumers and the code is
already parameterised for it. Everything in §9 does not.

## 9. Considered and declined

Each names the trigger that would change the answer.

- **`laterite-transport`** — the cleanest standalone crate in either tree: ~450
  lines, one file, `age` + `zstd` + `thiserror`, and its own header says
  "Content-agnostic (any file) and FS-only — no AGS knowledge", with documented
  interop against Python `pyrage` and the browser `age-encryption` library.
  Declined: nothing outside `laterite` wants it. *Trigger:* a second consumer.
- **`laterite-ags4-excel` and this repo** — not competitors but two halves of one
  problem. That crate generates a workbook from nothing, where whole-workbook
  serialisation is correct; this one changes cells in a vendor template and touches
  nothing else, where re-serialisation is disqualifying — which is the reason this
  repo exists. Nothing moves. *Action instead:* narrow that crate's open-ended
  "slated for rewrite into a general Excel library" note to record the boundary,
  and name `xlsplice` as the dependency if `laterite` ever needs to write into an
  existing workbook.
- **The AGS4 domain crates** —
  `laterite-ags4-{types,parse,reference,core,emit,validator,diff,trust,hostopts}`.
  The dictionary-single-source argument applies with full force: one line of
  `ags_dictionary.json` currently rebuilds the `#[pyclass]` codegen, the type
  stubs, the validator's per-edition tables and the wasm dictionary in one commit.
  Splitting any of them turns that into a cross-repo publish dance. *Trigger:* none
  foreseeable.

## 10. Verifying the claims here

Re-run the instruments rather than trusting the figures above.

```bash
# §3.2 — does the core run stdlib-only, outside the workspace, in seconds?
cd <laterite>
uv run --no-project python ags-wiki/.bootstrap/librarian.py \
  --paths rust-packages/laterite-ags4-reference/src/dict.rs
uv run --no-project python ags-wiki/.bootstrap/reindex.py --check
uv run pytest tests/test_librarian.py -q      # the synthetic-vault suite that travels

# §3.4 — confirm the blocker before planning around it
python -c "import sys; sys.path.insert(0,'ags-wiki/.bootstrap'); import lint"

# §5 — the publish flags the no-publish route depends on
grep -n publish rust-packages/laterite-cliutil/Cargo.toml
grep -rn publish rust-packages/{laterite-cli,laterite-ags4-corpus-qa,laterite-ags4-forge}/Cargo.toml

# §7 — size the gap before deciding what fits the CI budget
cd <xlsplice> && cargo clippy --all-targets && cargo fmt --check
```

Read `ags-wiki/design/dec-monorepo-structure.md` before acting on anything in the
crate tier. A carve-out that does not cite a fired trigger contradicts it, and the
house rule there is to surface that and stop rather than override it.
